# 阶段门判据

> 每道门的判据都是**可勾选的客观条件**，不是「感觉差不多了」。
> gate 汇报必须逐条对照，未达标的写明原因与补救动作。`SKILL.md` 的表格只是速查。

## 每道门共同的交互前置条件（8 个阶段都适用）

判据达标只是一半，另一半是使用者的决策必须被采集、复述、留痕（细则见 `交互协议.md`）：

- [ ] 已跑 `study.py ask <N>`，把该阶段决策点一次性打包给用户（Stage 0 为 15 个：E1–E2 + M1–M3 + D1–D6 + 0.1–0.4）
- [ ] 用户的选择确实改变了本阶段产出
- [ ] 文档里 `用户` 与 `[AI 建议]` 严格分开
- [ ] gate 逐条复述「决定 + 理由 + 来源」，用户认可后才 `pass`

---

## Stage 0 · 问题界定与需求澄清

- [ ] M1 交付形态已定，并据此裁剪检查点（求解器直用不必自研算法；论文形态不许省下界）
- [ ] M1=求解器直用时，M2 优化目标已选定（总时间 / 首解时间 / 证明时间 / 稳定性），且与业务诉求一致
- [ ] M3 允许动到哪一层已定（对象仅限本轮自己的模型）；越界项已重新征得同意
- [ ] 入口分诊已定（场景+数据 / 场景无数据 / 数据无场景 / 只有 idea），**且该入口的第一步产出已经写出来，不是只勾了一个入口名**
- [ ] 场景+数据时：数据充足性判定 A/B/C 已落到「缺哪几项、缺了导致目标改什么」
- [ ] 数据无场景时：§0.9 已填 ≥3 个目标不同的候选场景 + 各自 A/B/C 充分性标注 + 一个保守选项 + 排除理由 + 场景来源标注（未确认 / 已确认）
- [ ] 场景无数据时：§0.86 每个决策变量都有采集方案（参数 → 字段 → 来源 → 时间窗 → 责任人 → 缺了怎么降级）
- [ ] 只有 idea 时：§0.85 四问逐条落到 岗位名 / 决策频率与时间窗 / 可执行动作 / 含**分母**与现状值的指标；写「相关部门」「定期」「优化资源配置」一律算未答
- [ ] 数据契约写清来源类型与具体来源，版本/校验和已锁定；E2/E4 允许「未闭合」，但必须写明卡在哪、何时闭合，并在 §6 认下「Stage 1 只做构造性可行解、结论不报改善幅度」

### 入口 × 第一步产出（分诊不是勾选项）

| 入口 | 第一步产出 | 落在哪一节 | 「没做」的典型表现 |
|---|---|---|---|
| 场景+数据 | 数据充足性判定 | §0.6 / §0.7 | 直接开始建模，审计留到 Stage 3 |
| 场景无数据 | 数据需求反查表 + 取数方案 | §0.86 | 拿合成算例顶上，还说「先跑通再说」 |
| 数据无场景 | ≥3 个目标不同的候选场景卡 | §0.9 | 因为数据里有成本列就把目标设成成本 |
| 只有 idea | 场景化四问 | §0.85 | 直接跳到「这是个 VRP」，谁做决定、多久做一次全靠猜 |

> 只有 idea 时还有第二道：四问答完若「怎么算好」出现**多个互斥分母**（元/月 vs 元/单 vs 元/吨公里），
> 说明目标还没定，必须补 §0.9 让用户选口径——不许替用户挑一个顺手的。
- [ ] 按来源类型完成强制动作：提供→审计；公开→锁版本与参考值；合成→生成器规格与种子
- [ ] 参考值标了 OPT / BKS / LB，或明确写「无参考值」
- [ ] 数据使用边界写定：能否外推、能否声称实际效益
- [ ] 已跑 `data_profile.py` 出画像，缺失率与**缺失结构** / 主键重复 / 量级异常 / 规则违规四项有具体数字
- [ ] 清洗口径已定：哪些记录可删可改、判据是什么；原始文件只读，派生层可由脚本重建
- [ ] 清洗动作表已建，每步有对象、动作、判据、影响行数与理由
- [ ] 三档清洗策略（保守/基线/激进）已定义，并排入 Stage 6 敏感性小节
- [ ] 参数来源表已建：每个参数标了查表/实测/拟合/挖掘/假设，无出处者标 `[假设]`
- [ ] 挖掘产物落到模型具体位置（参数/情景/约束/初始解），写了验证方式与不采用时的影响
- [ ] 一句话陈述含决策、目标、约束、粒度、尺度
- [ ] 归入某个标准问题族，差异逐条列
- [ ] 复杂度 / 可解规模 / 近似比等已知结论已定位，标注是否核对原文
- [ ] 贡献点与最近 3 篇工作的差异可比较
- [ ] 参数台账三标注齐全
- [ ] 明确不做什么

**常见不合格**：只说「这是个优化问题」；文献只列名字不列结论；贡献写成「我们做了实验」；**数据来源留空、写「到时候再找」，或拿合成算例冒充真实数据**。

## Stage 1 · 可行解与校验器

- [ ] 至少一个具体可行解，逐条核对约束
- [ ] 校验器不依赖求解器，能返回违约码
- [ ] 违约码覆盖全部约束，含耦合约束
- [ ] 至少一组反例被正确拒绝
- [ ] 给出初始上界与平凡下界

**耦合约束的识别法**：约束左端是「多个决策变量之和」、右端是容量/上限/时间窗，就是耦合的——
它不能逐单判断，必须在方案装配完整后统一算。这类约束要**单独一码**，否则「每单都派了、都兼容、
但一台机要干 12 天」的方案会被判通过。反例测试里必须为它准备一个「合法但做不完」的算例。

**常见不合格**：只写「显然可行」；校验器直接调求解器；反例测试缺失；反例全是「漏派/重复」
这种一眼可见的错，没有一条是「结构合法但不可行」的。

## Stage 2 · 数学模型

- [ ] 集合 / 参数 / 变量 / 目标 / 约束齐备，量纲一致
- [ ] **目标函数的分母已声明**：min-max / 求和类目标写的是原始单位（h、件、元），还是可比单位（÷产能、÷速度、÷产出）
- [ ] 每条约束有业务解释、硬软、违约码、规模
- [ ] 至少两套等价 formulation，**实测** LP 松弛值
- [ ] 非线性已线性化，Big-M 最小合法并说明来源
- [ ] 复杂度与精确可解规模明确
- [ ] 对称性已处理或说明

**分母判据怎么用**：把目标写回原始单位再算一遍。若改善幅度从 20%+ 掉到个位数，
或者最优解换算成日历时间后物理上做不完（例如一台机一周要干 8 天），说明分母错了。
三台机速度差 3 倍时，原始工时均衡的解会让最慢那台排到 10 天——目标「更优」，方案「做不完」。

**常见不合格**：只写一套；说「约束更少更好解」但没测；Big-M 用 $10^9$；LP 松弛和 MILP 用了不同约束集；
目标写成「最小化总工时/总成本」却没说清是**净加工**还是**含等待**、是**单机口径**还是**全厂口径**。

**硬判据**：LP 界必须 $\le$ 整数解；不同 formulation 的整数最优值必须相同。

## Stage 3 · 数据与基线

- [ ] 算例来源可复现（库版本或生成器 + 全部种子 + 参数）
- [ ] **算例是真实数据还是合成数据，已明写**；合成时必须显式认下三条限制（结论只写算法相对表现 / 敏感性用假设区间做 / 交付带「数据为合成」字样），并用 `pass 3 --accept-synthetic` 留痕
- [ ] 规模分档有用途，验证档与主实验档分开
- [ ] 基线可复现，标明是否带最优性证书
- [ ] 参考值类型（BKS / LB / OPT）写清
- [ ] 硬件与时间口径写明

> **为什么「可复现」这条不够**：它的措辞是「库版本 **或** 生成器 + 种子」——合成算例天然满足，
> 于是一个一张真实数据都没有的研究可以合规通过 Stage 3，再一路把「降 x%」写到 Stage 7。
> 唯一拦住它的是 `00_问题界定.md` §0.6 的一句文字纪律，**没有任何程序化校验**。
> 实测：E4（只有一句 idea）入口下，Stage 3 原本静默放行了全合成的研究（见踩坑 I13）。

**常见不合格**：临时随机造几个点；把启发式最好解当 BKS；基线只用贪心；时限比基线松；
**用合成算例通过 Stage 3 却不写使用边界**。

## Stage 4 · 精确求解与可信度

- [ ] 精确方法选型有理由，写明时间/规模上界
- [ ] 求解器参数与诊断字段齐全（ObjVal/ObjBound/MIPGap/NodeCount/Runtime/Status）
- [ ] 至少一个合法下界，验证 $LB\le z_{IP}$
- [ ] 小规模独立精确解（枚举/DP/另一求解器）逐位对照
- [ ] 精确可解边界与超界降级方案明确
- [ ] （M1=求解器直用）调优前后同口径：同机、同线程、同时限、同 gap，**各档目标值一致**
- [ ] （M1=求解器直用）加速归因到层级（formulation / 参数 / 求解方式），失效参数也照写
- [ ] （M1=求解器直用）给规模边界：这套配置在多大内可证最优，超界给什么

**常见不合格**：只给目标值就说「最优」；拿启发式解当下界；没有独立验证；超时仍写「求得最优」；**调优只报"快了 3 倍"却不报线程数与目标值是否一致**。

## Stage 5 · 算法设计

- [ ] 算法结构清晰，伪代码可照实现
- [ ] 范式与问题结构匹配的论证（按 `算法手册.md` §1.1 映射表，不是「因为常见」）
- [ ] 解的表示与增量评价明确，单步复杂度可控
- [ ] **增量评价已与全量重算逐移动对撞**（`selftest.check_delta` 或等价实现，记录结果）
- [ ] 算子库完整，每个算子有作用与复杂度
- [ ] 参数、调参方式、调参预算、终止判据齐全
- [ ] 未在测试集上调参
- [ ] 理论义务按 `证明规程.md` §0 四类勾选（正确性 / 近似比 / locality gap / 难度），做了哪个写哪个
- [ ] 无理论保证时，明写「仅经验评估」，且全文不出现「保证」「ρ-近似」
- [ ] 随机性可控，种子与并行影响已说明

**常见不合格**：参数没来源；只有伪代码没跑过；增量评价没对撞就当它对；把「几个算例上达到最优」写成保证；声称近似比但没给紧例；邻域不连通却没讨论。

## Stage 6 · 结果验证与灵敏度

- [ ] 口径在跑之前写下，对照臂与配对键明确
- [ ] 主表含规模、参考值、各臂 obj 与 gap、时间
- [ ] 汇总指标含 gap 分布与最优解个数，不只报平均
- [ ] 超时/失败单列，不混进均值
- [ ] 统计检验方法、效应量、并列处理写明
- [ ] 消融/敏感性有清单，结论翻转照写
- [ ] 失败案例有分析
- [ ] **模型含时间推演时，做过三口径对照**：观测真值 / 模型重放现状 / 模型优化

**三口径为什么必须有**：模型日历（班次、换版、等待、返工）永远比现实乐观。
直接比「优化后 vs 优化前」，两边的偏差会互相抵消，看起来改善很大。
用「模型重放现状」当桥：重放 vs 观测 = 模型偏差，优化 vs 重放 = 优化贡献。
实测例：加急单观测逾期 9.8%，模型重放现状 3.9%，优化后也是 3.9%——
真实的结论是「指派不改善交期」，而不是「优化把逾期从 9.8% 降到 3.9%」。

**数据侧敏感性缺一项就不算「稳健」**：清洗三档、产能/速度口径、缺失参数的扫描区间、
以及「参数是否随机台变」（同一工件换设备后工时是否变）——任一没测，结论只能写「依赖该口径」。

**常见不合格**：平均值对平均值；把超时当 0 gap；只报显著结果；子集结论写成全量。

## Stage 7 · 方案交付与结论

- [ ] 每条结论有数字、证据强度、适用条件、来源实验
- [ ] 贡献 ≤3 条，与实验一一对应
- [ ] 图表与正文逐格一致，来源可追到 CSV
- [ ] 局限与未测清单成文，负结果不删
- [ ] 复现包干净环境可跑通
- [ ] 预设 ≥5 个审稿人问题及回答

**常见不合格**：把单例观察写成普遍结论；「局限」只有一句「未来工作」；复现缺参数。
