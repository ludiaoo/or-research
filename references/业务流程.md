# 业务流程 · 六环节的输入、产出与交付标准

> 这份文档回答一个问题：**每一环节做到什么程度才算交付，而不是「写完了」。**
> 判据都写成可勾选的条目；勾不上就是没做完，不许用「基本清楚」过关。

---

## 0. 交付物总览

| 交付物 | 主要读者 | 必须含 |
|---|---|---|
| 需求与数据说明 `00_问题界定.md` | 业务方 + 技术方 | 一句话问题、业务规则→约束映射、数据契约、边界与降级 |
| 可行性基准 `01_可行解.md` | 技术方 | 一个具体可行解、独立校验器、违约码表、反例测试 |
| 模型说明 `02_模型卡.md` | 技术方（业务方读摘要） | 符号表、目标分项、约束编号与业务来源、线性化、规模公式 |
| 数据与基线 `03_算例与基线.md` | 技术方 | 算例来源与版本、分档用途、基线清单、参考值类型 |
| 求解结果 `04` / `05` | 技术方 | 六字段、解文件、校验通过记录、算法适用条件 |
| 验证与灵敏度 `06_计算实验.md` | 业务方 + 技术方 | 现状对照、异常解释、参数曲线、稳健区间与翻转点 |
| 方案与结论 `07_交付与结论.md` | 业务方 | 结论分级、执行清单、局限、复算方式 |

## 1. 需求澄清与数据契约

### 输入

| 类型 | 内容 | 缺了怎么办 |
|---|---|---|
| 必备 | **入口状态**：场景+数据 / 场景无数据 / 数据无场景 / 只有一句 idea | 没说 → 必问。四种入口的第一步动作完全不同（审计 / 取数 / 构思场景 / 场景化），猜错整轮走偏 |
| 必备 | **使用意图**：是「只要解出来」还是「要能证明 / 要能上线执行」 | 没说 → 必问。三种意图对应三套裁剪路径，猜错整轮白做 |
| 必备 | 业务场景一句话、决策周期（一次性/每日/每周）、决策人、执行人 | 缺决策人或执行人 → 方案无法落地，先问清 |
| 必备 | 目标口径：优化什么、以什么为单位衡量 | 说「降本」但不说降哪块成本 → 追问到具体科目 |
| 可选 | 历史数据、现状做法（基线）、预算与时限 | 无现状基线 → 改善幅度无法计算，必须补 |
| 可选 | 现有模型 / 现有求解配置（已建模时） | 求解器直用时必须有：模型、当前耗时、机器与线程口径 |
| 数据在手时必备 | 原始文件（只读）、字段说明、单位口径、时间范围 | 缺字段说明 → 先画像再问，禁止按列名猜含义 |

### 动作

`study.py ask 0` 采集四组：**E1–E2（入口）→ M1–M3（意图与路线）→ D1–D6（数据）→ 0.1–0.4（定位）**。

- M1 = 求解器直用 → 转 `求解器调优.md`，用 `solver_bench.py` 出参数对照；本环节仍需锁定数据与现状耗时。
- M1 = 自研算法 / 完整研究 / 业务方案 → 按 8 检查点走。
- 数据来源按 `算例与基准.md` §0 的三分类处理。
- **数据到手先画像**：`data_profile.py` 出错失率、重复、量级异常、规则违规四项数字；再按 `数据清洗与挖掘.md` 定 D5 清洗口径与 D6 参数来源。
- 清洗动作写进动作表（对象/动作/判据/影响行数/理由），原始文件保持只读。

### 产出结构（`00_问题界定.md`）

1. **一句话问题陈述**：在 ____ 约束下，调整 ____，优化 ____，交付给 ____ 使用。
2. **业务规则 → 约束映射表**：规则 | 对应约束编号 | 硬/软 | 依据来源（谁提的、哪份文件）。
3. **数据契约**：来源类型、具体来源与版本、有无参考值、处理权、使用边界、清洗口径、参数来源。
4. **数据底账与清洗**：文件清单、画像结果、清洗动作表、三档清洗策略。
5. **参数来源与挖掘产物**：每个参数的来源类型与依据；挖掘产物进模型的位置与验证方式。
6. **候选场景卡（仅 E3 / E4）**：≥3 个目标不同的候选 + 各自 A/B/C + 一个保守选项 + 排除理由 + 场景来源标注。
7. **研究边界**：明确不做；无解或数据不足时的降级。
8. **参数台账**：`[给定] / [假设] / [扩展]` 三标注，[假设] 逐条经用户确认。

### 交付标准

- [ ] 一句话四要素齐全：约束、决策、目标、使用者
- [ ] 业务方通读后能说「对，就是这个」或指出偏差；不许默认通过
- [ ] 每条业务规则标了硬/软；硬约束里不出现「尽量」「优先」这种模糊词
- [ ] 数据四项已定：来源、参考值、处理权、使用边界
- [ ] 若入口是「数据无场景」：候选卡 ≥3 且目标互不相同、含一个保守选项、标明场景来源是否已确认
- [ ] 写了「什么情况下无解」，以及无解时怎么办

### 常见失败

- 目标写成「降本增效」，却没定义降哪项成本、增什么效 → 后面所有数字都无口径。
- 多目标不说优先级，最后用一组拍脑袋权重冒充结论。
- 忘了问现状基线 → 环节 4 算不出改善幅度，只能报绝对值。

## 2. 数学建模

### 输入

环节 1 的产出；数据结构（字段、粒度、时间窗、单位）；业务规则的硬软划分。

### 动作

符号化变量/参数/集合 → 写目标 → 写约束（逐条编号）→ 线性化 → 小算例手算 → 规模估算 → 两套 formulation 对比。

### 产出结构（`02_模型卡.md` + `01_可行解.md`）

| 段 | 内容 |
|---|---|
| 符号表 | 集合、参数（含单位）、变量（含类型与取值范围） |
| 目标 | 分项列出，每项对应一句业务口径 |
| 约束 | 编号 `C1..Cn`，每条注明业务来源与硬/软 |
| 线性化 | 非线性项、Big-M 取值与合法性论证（为何不能再小） |
| 可行解 | 一个具体解 + 校验器 + 反例测试 |
| 强度对比 | 两套 formulation 的 LP 界、约束数、节点数 |
| 规模公式 | 变量数/约束数随 n 的增长式 |
| 偏离清单 | 模型未纳入的业务规则，以及为什么 |

### 交付标准

- [ ] 每个变量有业务含义与单位；没有「只是为了凑公式」的变量
- [ ] 每条约束能指回一句业务规则；指不回的必须标「技术性约束（如 MTZ 消除子回路）」
- [ ] 目标每一项都能在数据里找到对应参数
- [ ] 有 n ≤ 10 的手算算例，模型解与手算逐项一致
- [ ] LP 松弛实测并记录；界太松要说明原因（如 Big-M 退化）与对策
- [ ] 规模公式能回答「客户数到 1000 还解不解得动」

### 常见失败

- 变量写了却不出现在目标或约束里（退化变量），白增规模。
- Big-M 随手取 $10^5$：数值不稳，或把可行解切掉。
- 只写一套 formulation，不做强度对比 → 环节 3 的算法效果无法归因。

## 3. 算法选型与求解

### 输入

模型；算例（含规模分档）；时限与硬件预算；基线方案。

### 动作

按「规模 × 结构 × 时限」选精确或启发式 → 实现 → 求解 → 独立校验 → 记录六字段。

### 产出

`04_精确解与下界.md` 或 `05_算法设计.md`；解文件（JSON/CSV）；运行日志。

### 交付标准

- [ ] 选型有理由：为什么这个规模用精确/启发式，不是「因为我会写 ALNS」；按 `算法手册.md` §1.1 映射表核对过
- [ ] 每次求解六字段齐全：状态、目标值、下界、gap、节点数、时间
- [ ] 解过**独立校验器**（不调用求解器判可行），0 违约
- [ ] 小规模与暴力枚举/DP 逐位一致
- [ ] 随机算法记录种子与重复次数；不许只报最好那一次
- [ ] **启发式另加三项自测**：增量 vs 全量、可行性一致、同种子可复现（`scripts/algotemplates/selftest.py`）
- [ ] 声称理论保证时，已按 `证明规程.md` 分清是正确性/近似比/locality gap 中的哪一种；否则明写「仅经验评估」

### 常见失败

- 只报「已求到最优」，不写 gap 与时限 → 无法判断可信度。
- 拿求解器自带的可行性判断当校验 → 模型写错时它也会说可行。
- 调参用了测试集 → 效果虚高，换算例就崩。
- 增量评价没对撞过 → 不报错，只让搜索方向系统性偏移，表现为「算法能跑但搜不到好解」。
- 破坏-修复不闭环 → 客户端静默丢失，或大量迭代浪费在不可行解上。

## 4. 结果解读与验证

### 输入

解；模型；现状基线；业务规则。

### 动作

反算每个关键数字 → 与现状同口径对比 → 查异常（退化、并列最优、反直觉分配）→ 标注不可行或部分不可行。

### 产出

`06_计算实验.md` 的验证节 + 方案对照表（按客户/时段/资源维度展开）。

### 交付标准

- [ ] 每个要写进报告的数字都能追到变量取值
- [ ] 与现状基线同口径；改善幅度写清分母（相对谁、哪些算例）
- [ ] 检查并列最优：同目标值是否存在多个方案？若存在，说明选了哪个、为什么
- [ ] 解释反直觉结果：为什么这个客户给无人机、为什么这辆车空驶
- [ ] 不可行/部分不可行的情形单列，不藏在正文里

### 常见失败

- 把目标值下降直接说成「省了 X 万元」（口径不同，单位不同）。
- 忽略并列最优，业务方执行时发现和方案不符。
- 不解释反直觉分配 → 业务方不信任，方案推不动。

## 5. 灵敏度分析

### 输入

参数台账；基线解；各参数的业务波动范围。

### 动作

单参数扫描 → 关键两因素组合 → 定位翻转点 → 给稳健区间。

**数据侧另有两条必做的敏感性**（与参数扫描并列，不合并）：

- **清洗敏感性**：保守 / 基线 / 激进三档口径各跑一遍，看目标值与解的结构是否翻转；
- **参数来源敏感性**：把 `[假设]` 与「挖掘估计」的参数换成保守/乐观值，看结论是否变。这两条回答的是「结论有多依赖数据决策」，与「参数浮动 ±10%」不是同一个问题。

### 产出

`06_计算实验.md` 的敏感性节：参数-目标曲线、稳健区间表、翻转点清单、清洗口径对照表。

### 交付标准

- [ ] 覆盖 ≥3 个关键参数，并说明为何选它们（影响大 / 不确定 / 业务关心）
- [ ] 每个参数给出扰动范围与步长，且与业务实际波动匹配
- [ ] 给出**稳健区间**（结论不变的范围）与**翻转点**（结论改变的点）
- [ ] 至少一组两因素交互（如 需求 × 单位成本）
- [ ] 清洗三档与假设参数两个来源都测过，翻转的已降级为「依赖口径/依赖假设」
- [ ] 明确「哪个参数一动结论就变」，并给业务方可执行的监控建议

### 常见失败

- 只扫一个参数，还扫的是无关紧要的那个。
- 画了曲线就交差，「趋势平稳」不是结论；要说「±20% 内方案不变，超过 30% 才翻转」。
- 扰动幅度拍脑袋（±50%），与业务真实波动无关。

## 6. 方案与结论交付

### 输入

前五环节全部产物。

### 动作

结论分级 → 写执行清单 → 列局限 → 打包复现 → 业务方复述验证。

### 产出结构（`07_交付与结论.md`）

1. 结论摘要：3–5 条，每条带强度标记。
2. 执行清单：谁 / 何时 / 做什么 / 依赖什么。
3. 方案对照：现状 vs 优化，按维度拆分差异。
4. 稳健性与适用条件（来自环节 5）。
5. 局限与未测（≥3 条）。
6. 复算方式：环境、数据版本、命令、预期输出。

### 交付标准

- [ ] 结论分三级：**确定**（有证书或多算例）/ **有条件**（在某参数区间内成立）/ **仅本算例**
- [ ] 执行清单可直接排期：有责任人、时间、输入依赖
- [ ] 每个百分比带分母与口径
- [ ] 局限 ≥3 条且具体（不写「未来可进一步研究」）
- [ ] 干净环境按复现清单能跑出同一张表
- [ ] 业务方能在不看公式的情况下复述方案要点

### 常见失败

- 写「效果显著」却不给量级和成立条件。
- 只给推荐方案，不解释「为什么不选那个看起来更省的」。
- 复现包缺种子或版本，三个月后自己都跑不出来。

## 7. 三条跨环节通用要求

| 要求 | 具体做法 |
|---|---|
| **可复用** | 目录固定 `data/ code/ results/ figures/`；解与报告命名 `环节_对象_版本`；模型用 JSON 描述，换场景只换数据与约束块 |
| **可解释** | 每个关键数字三问：从哪来、可信吗、变了会怎样；答不上就别写进报告 |
| **可复算** | 记录解释器与依赖版本、求解器与许可、全局与各臂种子、数据校验和、命令顺序；`复现清单.md` 一次写全 |
