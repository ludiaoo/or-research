# 交互协议 · 把使用者的决策与思路问出来、记下来

> 默认流程若只有「AI 汇报 → 用户点头」，会产生一个隐蔽问题：**AI 把自己的默认选择当成「已确认的用户决策」**，
> 而使用者真正的判断、取舍理由、可接受的边界全都没进文档，到最后就变成「已知条件」。
> 本文件把每道门补成**双向交互**：开场采集 → 按回答产出 → 收尾复述确认 → 全程留痕。

## 1. 五条核心原则

0. **先问「你要什么」，再问「怎么做」**。同一句话可以是「只要解出来」「要能证明」或「要能上线」，三种意图对应三套裁剪路径。M1–M3 必须在 Stage 0 最开始问，不许默认按论文口径推进。
1. **AI 不替用户做决策**。可以给建议、给默认值，但必须显式标 `[AI 建议]`；只有用户明确给出的选择才写进「用户决策」。「用户没反对」≠「用户同意」。
2. **先问后做**。每阶段开工先问决策点，用户回答是**本阶段的输入**，不是事后再补的确认。
3. **收尾要复述，不要只问「确认吗」**。逐条复述「我理解你的决定是…理由是…来源是你的回答还是我的建议」，请用户确认或纠正；含糊、冲突、未答必须追问。
4. **决策与思路都要留痕**。写进 `state.json` 和阶段文档的「本阶段决策与思路」表；最终交付要能一眼看出每个关键取舍是谁定的、为什么。

## 2. 三段式协议

### 开场 · 采集决策（Stage N 一开工就做）

```bash
python study.py ask <N> --study <研究目录>
```

`ask` 会列出该阶段 **必须由用户拍板** 的决策点及 AI 建议默认值（每阶段 4–6 个，Stage 0 为 15 个：E1–E2 + M1–M3 + D1–D6 + 0.1–0.4）。AI 一次性打包提问，不要一条一问：

```
【Stage N 开工前 · 请先定这几件事】
1. <决策点>？常见做法 A / B；我建议 A（[AI 建议]，理由…）。你的选择是？
2. ...
可以只回「编号 + 选择 + 一句理由」。没指定的我会按建议做，
但会标成 [AI 建议]，收尾时单独再跟你确认一次。
```

### 执行 · 按回答产出

- 把回答逐条写进阶段文档的「## 本阶段决策与思路」表，`来源` 列区分 `用户` / `[AI 建议]`。
- 用户的选择**改变产出**（模型写法、算例、算法、口径），不是只改一句描述。
- 回答含糊或与已有决策冲突：**停下来追问**，见 §4。

### 收尾 · 复述确认

```
【Stage N · 决策复述 · 请确认或纠正】
| # | 决策点 | 我理解你的决定 | 你的理由 | 来源 |
|---|---|---|---|---|
| 1 | ... | ... | ... | 用户 / [AI 建议] |

出口判据：逐条 ✅ / ⬜
OR 工件：本阶段应交付的工件是否齐全
以上如无异议，我记为已确认并进入 Stage N+1；
有哪条不对，直接说编号 + 改成什么。
```

用户明确认可后才运行：

```bash
python study.py pass <N> --note "<用户确认了什么>" \
    --decision "N.1=<用户选择>" --decision "N.2=<用户选择>" \
    --rationale "<用户的思路>" --study <研究目录>
```

`--decision` 可重复；`--rationale` 记**用户的思路**，不是 AI 的解释。
所有 `[AI 建议]` 项必须在 `--note` 或 `--rationale` 里写明「已在 gate 单独确认」。

## 3. 8 阶段决策点清单

> `study.py ask <N>` 打印同一份清单。每阶段 4 个问题（Stage 0 另加 2 个入口问题 E1–E2、3 个意图问题 M1–M3 与 6 个数据契约问题 D1–D6，共 15 个），一次性打包问完。

### Stage 0 · 问题界定与需求澄清

> **四组顺序不能颠倒**：先问 E1–E2（手上有什么），再问 M1–M3（要什么强度），然后 D1–D6（数据：来源/参考值/处理权/边界/清洗口径/参数来源），最后 0.1–0.4（定位）。
> 入口问错了，第一步就做错事：只有数据的人被拖去找算例，有场景没数据的人被拖去建模。

| # | 必须用户拍板 | 为什么 | 常见选项 / AI 建议 | 含糊信号 → 追问 |
|---|---|---|---|---|
| E1 | 入口状态：场景+数据 / 场景无数据 / 数据无场景 / 只有一句 idea | 四种起点对应四个不同的第一步 | 按「有无场景 × 有无数据」二分定位 | 「我有点数据」→ 追问：这些数据里有没有你想优化的那个决策？ |
| E2 | 若只有数据：目标从哪来（我提候选你选 / 你直接给 / 先做描述性分析） | 目标不能由数据字段倒推 | 我提 3 个目标不同的候选场景；保守选项必含 | 「你看能优化啥」→ 明确告知会出 3 个候选并标数据充分性 |
| M1 | 交付形态：求解器直用 / 自研算法 / 完整研究 / 业务方案 | 决定走哪条裁剪路径、要哪些检查点 | 能上求解器先上；规模明显超出或有算法贡献才自研 | 「就优化一下」→ 给三条路线的产出对比，请他选 |
| M2 | 求解器直用时优先优化哪个时间：总时间 / 首解时间 / 证明时间 / 稳定性 | 三者调法不同甚至相反（MIPFocus=1 与 3） | 业务要方案选首解；要证书选证明时间 | 「越快越好」→ 追问是「多久能给方案」还是「多久能证明最优」 |
| M3 | 允许动到哪一层：只调参数 / 动本次研究的 formulation / 动求解方式 | 越界会改变结论强度（L3 之后只剩启发式解） | 先 L1/L2；动 L3 需把结论降级 | 「都行」→ 先说明「动的对象是本轮自己写的模型，不是别人的代码或原文」；再说明动 formulation 可能改变解的结构，请他确认 |
| D1 | 数据从哪来 | 决定这条研究能不能做、要不要先补数据 | 使用者提供 / 公开基准（AI 检索）/ AI 合成 / 混合 | 「你随便找点」→ 请他在「我检索公开基准」与「我合成」之间明选，并说清差别 |
| D2 | 有没有官方参考值（OPT / BKS / LB） | 没有参考值就无法算 gap、无法说「更好」 | 有就落地并标类型；没有就只自建基线 | 「应该差不多」→ 要求指出具体文件或明确写「无参考值」 |
| D3 | 允许对原始数据做哪些处理 | 处理不可追溯 = 结果不可复现 | 原始只读；清洗裁剪写成脚本；是否允许补齐规模档 | 「你看着洗」→ 逐项问：可以删点吗？可以重采样吗？可以裁剪规模吗？ |
| D4 | 结论能用到哪（外推 / 实际效益） | 防止用合成数据讲真实收益 | 仅本算例族；合成数据只写相对表现 | 「应该通用」→ 请他给可外推的边界条件，否则按不外推写 |
| 0.1 | 最接近哪个标准问题族，差异是什么 | 决定查哪批文献、套哪些已知结论 | 归入最接近的模型，差异逐条列 | 「就是个优化问题」→ 给出 2–3 个候选模型请他选 |
| 0.2 | 目标包含哪些项，什么算「更好」 | 决定后续所有数字的方向与量纲 | 单目标先做；多目标要权重或优先级 | 「综合考虑」→ 请逐项列并排序 |
| 0.3 | 规模与时间尺度上界 | 决定精确还是启发式路线 | 给 S/M/L 三档具体量级 | 「越大越好」→ 追问实际最大算例与时间预算 |
| 0.4 | 贡献点定位（新问题 / 变体 / 复现改进 / 算法） | 决定实验要支撑什么 | 按材料能支撑的最强定位往下取一档 | 「做出新东西」→ 逐条问与最近 3 篇的差异 |

### Stage 1 · 可行解与校验器

| # | 必须用户拍板 | 为什么 | 常见选项 / AI 建议 | 含糊信号 → 追问 |
|---|---|---|---|---|
| 1.1 | 什么算合法解，哪些约束绝不可违反 | 违约码与硬软划分的依据 | 先全硬 | 「按常识」→ 逐条请他裁定，不许 AI 代判 |
| 1.2 | 校验器是否必须独立于求解器 | 防止「求解器说可行就可行」 | 必须独立 | 无 |
| 1.3 | 初始可行解怎么构造 | 影响起点界与后续算法 | 贪心 + 手工各一个 | 「你构造一个」→ 构造后请他确认是否符合业务直觉 |
| 1.4 | 真不可行时怎么处理 | 防止偷偷放松约束 | 报错 + 违约码；不自动放松 | 「想办法弄可行」→ 说明放松会改变问题，请他裁定 |

### Stage 2 · 数学模型

| # | 必须用户拍板 | 为什么 | 常见选项 / AI 建议 | 含糊信号 → 追问 |
|---|---|---|---|---|
| 2.1 | 变量建模方式（指派 / 弧流 / 时间索引 / 析取图） | 直接决定规模与 LP 强度 | 先选维度最小的等价写法 | 「用最常用的」→ 给出两种写法的规模对比 |

| 2.4 | 软约束惩罚与多目标处理 | 改变可比口径 | 先全硬；多目标加权 + 权重敏感性 | 「都要满足」→ 确认是否真的可行 |

### Stage 3 · 数据与基线

| # | 必须用户拍板 | 为什么 | 常见选项 / AI 建议 | 含糊信号 → 追问 |
|---|---|---|---|---|

| 3.4 | 时间上限与硬件口径 | 跨论文比较的前提 | 单线程 + 明确时限 | 「越快越好」→ 追问上限秒数与线程数 |

### Stage 4 · 精确求解与可信度

| # | 必须用户拍板 | 为什么 | 常见选项 / AI 建议 | 含糊信号 → 追问 |
|---|---|---|---|---|
| 4.1 | 精确方法选型（MILP / CP-SAT / DP / B&P） | 决定能证到什么规模 | MILP + 小规模枚举验证 | 「用最好的」→ 给出规模-时间权衡 |

| 4.3 | 可接受 gap 与时间上限 | 决定何时停 | 小规模 gap=0，大规模 ≤1% 或时限 | 「算到最优」→ 追问大规模怎么办 |
| 4.4 | 小规模独立精确解的验证方式 | 防模型写错却「求解成功」 | 暴力枚举或 DP，逐位对照 | 无 |

| 5.6 | 实现交付形态（伪代码 / 可运行代码 / 骨架接入 + 三项自测） | 决定「能跑」还是「只能读」 | 可运行代码 + `selftest` 三项；骨架在 `scripts/algotemplates` | 「给个思路就行」→ 说明未经自测的增量评价不可信 |

## 4. 追问规则

| 用户信号 | 判定 | AI 必须做什么 |
|---|---|---|
| 「都行」「你看着办」「随便」 | **未做决策** | 给 2–3 个具体选项 + 各自后果，请用户选；不许按建议执行后写成「用户已确认」 |
| 「差不多」「大概」「尽量」 | 含糊 | 要求给具体数值/边界；给不出就标 `[AI 建议]`，gate 单独复述确认 |
| 与上一阶段决策冲突 | 冲突 | 指出两处原文，请用户裁定；裁定前**不推进** |
| 与某条出口判据冲突 | 风险 | 给「改判据 / 改方案 / 接受风险并写进局限」三选一 |
| 沉默、只回「嗯」「好」 | **未确认** | 门保持开启，不 pass；重发精简版清单 |
| 改主意 | 变更 | `study.py reopen <stage>`，清空后续确认与决策表；受影响结果全部重跑 |
| 只给选项不写理由 | 缺 rationale | 写「未另述理由，取舍含义以选项描述为准」，**不许替用户编理由** |

## 5. 留痕规范

`study.py pass` 会把下列字段写进 `state.json` 与本阶段文档：

| 字段 | 含义 |
|---|---|
| `decision` | `编号=用户的选择`，可多条 |
| `rationale` | **用户的思路/理由**，不是 AI 的解释 |
| `note` | 本次确认用户说了什么（含 `[AI 建议]` 项已单独确认的说明） |
| `source` | `用户` 或 `[AI 建议]`，不得混写 |
| `confirmed_at` | 确认时间 |
| `uncovered` | 未采集的决策点；`pass` 会主动报出，gate 须说明原因，不许静默略过 |

用 `study.py decisions --study <目录>` 汇总全部决策，**Stage 7 收尾必须跑一次并逐条复述**。

## 6. 反模式（不要这么做）

- 把「用户没反对」当成「用户同意」，直接 `pass`。
- 把 AI 默认值写进「用户决策」列，只在角落标一句「默认」。
- 一次抛 10 个以上问题；每阶段 4 个、一次性打包。
- 收尾只写「确认吗」，不复述决策与理由。
- 用户答了却不更新产出，只在 `--note` 里塞一句话。
- 用户含糊时自行脑补一个「合理」选择继续推进。
- 用户只选了选项，却替他补写一段「他的考虑是……」。
