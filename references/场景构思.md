# 场景构思 · 从数据或一句 idea 走到可建模的问题

> 适用入口：**E3（有数据、没有明确场景）** 与 **E4（只有一句 idea）**。
> 目标不是「想一个优化问题」，而是**找出这份数据真正能支撑的决策，并判定支撑到什么程度**。
> 这份规程的产物必须能让用户点头说「对，这就是我要决定的那个事」，而不是「听起来挺合理」。

---

## 1. 先画像，再构思

看到两列数据就开始写目标函数，是这类任务最常见的死法。先做画像，产出 `data/profile.md`。

| 问 | 要看什么 | 判错的后果 |
|---|---|---|
| 实体是谁 | 表里哪些列是「被安排的对象」（车、人、机台、订单、货位） | 把属性当对象，模型没有可决策量 |
| 决策粒度 | 一行代表什么？一次配送 / 一个班次 / 一笔订单 / 一个时刻 | 粒度错了，约束全部对不上 |
| 时间跨度 | 覆盖多少天、有无决策时刻、是否含执行结果 | 没有「决策时刻」就无法区分事前决策与事后结果 |
| 结果字段 | 哪些列是「做了之后才知道」的量（耗时、成本、是否延误） | 把结果当输入 = 用未来信息做决策 |
| 约束线索 | 容量、班次、载重、地理范围、资质 | 漏掉硬约束，方案不可执行 |
| 缺失结构 | 哪些字段缺失率高，缺失是否与对象相关 | 缺失非随机时，任何统计结论都会偏 |

**画像的完成标准**：每个字段一行——名称、类型、单位、取值范围、缺失率、能否作为决策对象或约束来源。

## 2. 三条从数据到场景的通道

不同数据形状对应不同的构思通道。先判断落在哪条，再按该通道的清单往下走。

| 通道 | 数据特征 | 典型场景 | 还要补什么 |
|---|---|---|---|
| **A 资源—任务匹配** | 同时存在「资源」与「任务」两类实体（车与订单、人与班次、机台与工件） | 指派、排产、路径、班表 | 资源能力参数（容量/速度/资质）、任务时间窗 |
| **B 时空聚集** | 有坐标与时间戳，但没有显式「任务」表 | 路径规划、区域划分、巡访计划、设施选址 | 把点聚成「服务对象」，定义服务频次与时长 |
| **C 成本结构** | 有成本/工时/能耗分项，决策是「怎么配比」 | 配载、混料、采购组合、能源调度 | 各项的边际关系（线性？有阶梯？有最小批量？） |

判据：**能指出「谁在什么时刻、从几个可选动作里选一个」**，才算摸到场景；指不出来就还在描述数据。

## 3. 数据充分性分级（决定结论能说多强）

| 级别 | 判定 | 能支撑的结论 | 不能说的话 |
|---|---|---|---|
| **A** | 目标所需字段齐全，且有历史决策记录可当基线 | 可建模、可与现状对比、可报改善幅度 | 仍不能说「外推到其他场景」 |
| **B** | 缺关键字段（无时间、无成本、无容量），但主体结构完整 | 可建模，但目标要换成数据支持的度量（最小化距离/最大化满足率/最小化延误） | 不能说「节省 x 元 / 降本 y%」 |
| **C** | 只有结果、没有决策，或关键维度整体缺失 | 只能做描述性分析、参数估计、或先补数据 | 不能做优化，不能报任何「提升」 |

### 目标 → 字段反查表

| 想优化的目标 | 必需字段 | 缺了会怎样 |
|---|---|---|
| 最小化总成本 | 单位里程/工时成本、固定成本、惩罚成本 | 只能退化为最小化距离或时间，且必须改口径 |
| 最小化完工时间 | 各工序/路段耗时、资源数量 | 缺耗时只能按距离代理，结论强度降一档 |
| 最小化延误 | 承诺时间、实际到达时间、延误惩罚 | 缺承诺时间就没有延误定义 |
| 最大化满足率 | 需求量、可供量、缺货规则 | 缺需求量只能做分配问题，不是满足率问题 |
| 最小化能耗 | 能耗率、负载关系、速度档 | 只有总量没有分项，无法优化结构 |

**纪律**：级别由字段判定，不由「我觉得差不多」判定；写成 B 就按 B 说话，不许在报告里悄悄升成 A。

### 3.1 产能类参数：能从时间戳反推，就别假设

「产能不足 / 负荷不均」这类结论几乎全靠一个数：**可用工时**。而这个数在数据里通常没有，
只有开工与完工时间戳。此时最容易犯的错是套一个行业默认值（「一天一班 8 小时」）。

**先看错误示范的后果**：某印刷厂 3 台机、387 张工单、5 个月，按 8h×5日 算，
总负荷 285%。机器不可能连续 5 个月超 100% 运转——**这不是「产能爆炸」的结论，是假设错了**。
真实情况是 P3 每天干 14.8 小时（两班倒），P1 只干 5.7 小时。

**正确做法：用时间戳反推三个数**（都不依赖班次假设）

| 指标 | 算法 | 说明什么 |
|---|---|---|
| 日强度 | 总工时 ÷ **有作业的天数** | 加班程度。> 12h 基本就是在靠加班顶 |
| 作业日覆盖率 | 有作业天数 ÷ 窗口内工作日数 | 停机/空转程度。< 70% 说明有明显空档 |
| 相邻工单间隙 | 同资源相邻工单的（后开工 − 前完工）中位数 | 排队与空闲。< 1h 说明该资源没有喘息 |

**判据**：任何负荷率 > 100% 的结果，先回头查产能口径，不许直接写「产能不足」。
只有当「反推强度」与「用户确认的班次」对得上时，负荷率才能进结论。

**这条不只影响描述**：它决定了候选场景的走向。本例若按 285% 判，结论会是「必须扩产」；
按反推口径，结论是「总产能接近饱和，但排产能把峰值削掉 20%」——后者才是可执行的方案。

## 4. 候选场景卡（至少 3 个，目标必须不同）

每个候选一张卡，八项填满才算合格：

```
场景一句话：
决策变量：        （谁、在什么时刻、选什么）
目标：            （度量 + 方向 + 单位）
硬约束：          （不可违反的业务规则，逐条对应数据字段）
数据支撑：        A / B / C  + 缺哪几项
规模量级：        实体数 × 时段数 ≈ 变量规模
业务解释力：      这条结论会被谁用来做什么决定
预期难点：        建模 / 求解 / 数据，哪个先卡住
第一个会被问的问题：
```

**三条硬规则**：

1. **三个候选的目标必须不同**。同一个目标换三种说法不算三个候选，那是浪费用户时间。
2. **C 级不许进候选**，除非用户明确接受「先补数据再建模」并写进计划。
3. **必须有一个保守选项**：数据最全、结论最弱、但能在一轮内交付。没有保守选项，用户只能在「理想但做不成」和「能做但没用」之间选。

## 5. 禁止事项

- **数据里有成本列，目标就设成成本最小**。目标来自业务问题，成本列只是可用字段；反过来定目标，等于让数据替你决定要做什么生意。
- **把相关性当可决策性**。「A 高的订单耗时更长」不等于「调整 A 能缩短耗时」。要能说清干预通道，才算决策变量。
- **用预测冒充优化**。需求预测是输入，不是决策；预测得准不等于方案更优。
- **B 级写成 A 级**。缺成本却报降本比例，是这类任务最常见的造假方式，而且往往不是故意。
- **只有 idea 就直接建模**。先过第 6 节的四问；答不出「谁在什么时刻做什么决定」，模型一定是错的。

## 6. 一句 idea 的场景化四问

| 问 | 答不出时的追问 |
|---|---|
| **谁** 做这个决定 | 岗位/角色是什么？他现在的做法是什么？ |
| **什么时候** 做 | 每天一次？每单一次？临时触发？周期决定粒度 |
| **决定什么** | 从哪几个可选动作里选一个？动作必须是可执行的（派谁、走哪条、做多少） |
| **怎么算好** | 用什么指标衡量？现在这个指标大概是多少？没有现状值就没有改善幅度 |

四问都答上来，才有一句话陈述；仍答不上就退回 E1（先找场景）或 E3（从数据找场景）。

## 7. 交接

1. 选定场景写进 `00_问题界定.md` §1 一句话陈述，并标「本场景由数据画像推得，尚未经业务方确认」——除非用户就是业务方。
2. 转 `算例与基准.md` §0 做数据契约：E3 走「使用者提供 → 审计」，E4 走对应的取数路径。
3. 数据升级到 A 级或明确接受 B 级口径后，才进 Stage 1 造可行解。

> **一句话判据**：如果候选场景卡里「数据支撑」这一栏全是 C，那现在该做的是补数据或做描述性分析，不是建模。
