# 数据清洗与挖掘（Stage 0.7 / 0.8）

> 一句话立场：**清洗和挖掘不是「预处理」，是参数生产**。模型里每个数字追到最后都是一次数据决策；决策改了，可行域就变，解就变，结论就变。
>
> 与机器学习的分野：ML 关心样本外预测精度，OR 关心**可行域形状与最优解位置**。被删掉的那个极端客户，往往正是决定路径结构、决定这条约束紧不紧的点。

---

## 0. 什么时候读这一篇

| 触发 | 动作 |
|---|---|
| 用户给了 Excel / CSV / 数据库导出 | 先跑 `scripts/data_profile.py` 出画像，再谈建模 |
| 数据来自多个表或多个系统 | 先做 §3.3 键与口径对齐，否则后面全是静默错配 |
| 模型参数里有「需求」「时长」「成本」这类要算出来的量 | 走 §5，把每个参数标上来源 |
| 用户说「数据太脏了，你帮我洗一下」 | 先问 §1 三闸，尤其是「允许删吗」 |
| 结论要写「节省 X%」 | §4 铁律 3 + §6 清洗敏感性，缺一不可 |

## 1. 三道闸（Stage 0 的 D3 / D5 / D6）

清洗最容易犯的错不是技术错，是**没经过授权就动了数据**，事后无法解释结论。

| 闸 | 问题 | 不通过的后果 |
|---|---|---|
| **闸一 · 处理权（D3）** | 原始文件能不能改？能不能删记录？能不能补造？ | 原始文件被覆盖，复现不可能；结论无法回溯 |
| **闸二 · 清洗口径（D5）** | 哪些记录允许删 / 改 / 补，判据是什么，由谁确认 | 「脏数据」变成「按结果需要的数据」 |
| **闸三 · 参数来源（D6）** | 模型里的数是查表、实测、拟合，还是假设 | 参数无法追溯，灵敏度分析无从下手 |

**默认口径（用户未特别说明时按此执行，并写入 `00_问题界定.md`）**：

1. 原始文件只读，一切清洗写在脚本里，输出到 `data/staging/`；
2. 允许删「可证明是录入错误」的记录，删除必须逐条给理由；
3. 不允许因为「删了之后模型更好解」而删记录；
4. 缺失与极端值默认**保留并标注**，是否处置由用户决定；
5. 参数默认标 `[假设]`，除非有明确出处。

## 2. 先画像，再动手

不要打开表就写 `dropna()`。先回答六个问题——答不上来的那一条，就是后面会翻车的地方。

| # | 问题 | 答不上来会怎样 |
|---|---|---|
| 1 | **一行代表什么**？（一个订单 / 一次配送 / 一天的汇总） | 聚合层级错，需求量整体放大或缩小 |
| 2 | **主键是什么**？是否唯一？ | 重复计数，成本被高估 |
| 3 | **时间跨度与粒度**？有无断档？ | 用「日均」时把停业期算进去 |
| 4 | **空间参照是什么**？经纬度 / 地址 / 网格 / 行政区？ | 距离口径错，里程结论全废 |
| 5 | **单位与口径**？元还是万元、分钟还是小时、含税还是不含税 | 参数差 100 倍 |
| 6 | **缺失与极端值长什么样**？成块还是零星 | 系统性缺失被当成随机缺失处理 |

### 2.1 用工具出客观画像

```bash
python "<SKILL_DIR>/scripts/data_profile.py" data/raw/orders.csv \
    --key order_id --time created_at \
    --rule "promised_at >= created_at" \
    --rule "weight_kg > 0" \
    --out data/raw/_profile.md
```

它给的是**事实**，不是判断：行数、缺失率、唯一值、分位数、IQR 外点数、主键重复、时间间隔、规则违规行数。判断仍要人做，但至少先有同一套数字。

### 2.2 画像要看的三件事

| 看什么 | 危险信号 | 往下查什么 |
|---|---|---|
| 缺失的**分布形状** | 某几列同时缺失、集中在某时间段/某仓 | 系统性问题（系统切换、某仓未接入），不是随机缺失 |
| 极端值的**可追溯性** | 无法回溯到原始凭证 | 大概率是录入错误；能追溯的极值要保留 |
| 键的**唯一性** | 主键重复率 > 0 | 重复录入 or 天然多事件（同客户同日多单），两者处置相反 |

## 3. 五类病灶：判定与处置

### 3.1 缺失

| 项 | 内容 |
|---|---|
| **判据** | 缺失率；缺失是否与目标量相关（按「缺失 / 非缺失」分组比较均值，差异 > 10% 就要警惕） |
| **处置**（按优先级） | ① 回溯补录 → ② 用同键其他记录推导 → ③ 插值/分组中位数 → ④ 保留为「不确定参数」→ ⑤ 删除（最后手段） |
| **留痕** | 每列写：缺失数、处置方式、依据、影响行数 |
| **对模型的影响** | 填均值会**压缩方差**，让需求看起来比实际更平稳；鲁棒/随机模型会因此低估所需缓冲 |

**OR 特有陷阱**：零售场景里「销量 = 0」既可能是真没需求，也可能是**缺货导致的零**。两者混在一起做需求估计，会系统性低估高需求点，进而低估库存与运力。判定方法：看同期的缺货标记 / 到货记录；没有标记就只能作为情景处理，不能当观测值。

#### 3.1.1 条件字段：缺失不是「没填」，是「只对某类行有定义」

高缺失率的列有两种完全不同的成因，处置也相反：

| 成因 | 判据 | 处置 |
|---|---|---|
| **条件字段** | 缺失由另一列**完全解释**：按该列分组后，每组要么全空、要么全有 | **不填值，改口径**：只在有定义的子集上算，并写明覆盖范围 |
| **成块缺失** | 缺失集中在某段时间 / 某个批次，按时间或批次分组后成块出现 | 查停业、系统切换、导出漏档；成块缺失不能当随机缺失处理 |

`data_profile.py` 会直接把第一种判出来，输出形如
「`交期` 缺失 336（86.8%）**由 `是否加急` 完全解释**」。

**为什么这是最危险的一类**：它不报错、不显眼，只是悄悄换了分母。

- 交期只在加急单上填（13%）→ 拿它算「全厂准时率」，等于用 13% 的样本代表 100% 的单；
- 成本只在自产件上填 → 算「平均单位成本」时，外购件被静默排除；
- 到货时间只在外购件上填 → 算「平均提前期」时，自制件凭空消失。

正确做法不是插值补全（那是在编造业务规则），而是三选一：
① 把目标改到定义的子集上（「加急单准时率」），并报告覆盖率；
② 向业务方补一个「全量口径」的字段；
③ 明确降级：这个目标本轮不可算，写进研究边界。

这也是红线 28（目标不许由字段倒推）在数据侧的镜像：**字段只覆盖一部分行时，目标就只能覆盖那一部分，不许悄悄放大**。

### 3.2 异常值

先分类，再处置。**同一堆「异常值」里通常混着两种完全相反的东西**：

| 类型 | 特征 | 处置 |
|---|---|---|
| **错误值** | 物理上不可能（负重量、速度为负、时间为负）；量级差 10/100/1000 倍；与其他字段矛盾；可回溯到录入环节 | 改（有正确值）或删（无正确值），逐条记录 |
| **真实极端** | 业务上解释得通（大促、大客户、恶劣天气）；可追溯；重复出现 | **保留**，并作为鲁棒性算例或压力测试点 |

**判据组合**（不要只用一条）：

1. 物理可实现性——违反常识的直接进「错误」候选；
2. 内部一致性——`送达时间 < 发出时间` 这类跨字段矛盾；
3. 重复性——同类极端是否反复出现（反复出现更像真实业务）；
4. 可追溯性——能否找到原始单据。

> **禁令**：不许用 3σ / IQR 一刀切删点。在 OR 里，极端值常常就是**约束最紧的地方**。删掉最难的 5% 客户，平均成本必然下降——这不是算法变好，是题目变简单。若一定要截尾，必须同时报告「截尾前后的解与 gap」，并在结论里写明「已排除极端算例」。

### 3.3 重复与冲突

| 症状 | 先分清 | 处置 |
|---|---|---|
| 同键多条 | 重复录入 vs 天然多事件（一日多单、一单多行明细） | 前者去重，后者**先定聚合口径**（按单 / 按日 / 按客户）再聚合 |
| 同一实体两个 ID | 主数据未合并（客户别名、仓库改名） | 建映射表并留档；映射表本身就是交付物 |
| 时间重叠 | 同一车辆/人员同时段两任务 | 可能是调度记录错，也可能是并行作业；问业务，别猜 |
| 状态不一致 | 订单「已取消」但有签收时间 | 以哪个为准要用户拍板，写进口径 |

**顺序不能反**：先定聚合口径，再做去重。反过来会把「一单多行」误删成一行，需求直接少一半。

### 3.4 口径不一致

这一类最隐蔽，因为**数据不报错，结果只是偏了一点**。

| 口径 | 常见坑 | 检查方法 |
|---|---|---|
| 单位 | km/m、分钟/小时、元/万元、kg/吨 | 与业务量级对照（城市配送 5 km 还是 5 m） |
| 时区 | UTC 与本地时间混用；跨日归属错 | 检查 00:00–08:00 的记录是否异常聚集 |
| 空间 | 经纬度 vs 投影坐标；球面距离 vs 路网距离 vs 曼哈顿 | 抽样 20 对点，用两种口径各算一次，比对差异 |
| 聚合层级 | SKU vs 品类、日 vs 周、单仓 vs 全网 | 各级求和是否与总数一致 |
| 货币/年份 | 名义价 vs 实际价；跨年未做通胀调整 | 成本类参数尤其要问清基准年 |

> **实例教训**：自写 Haversine 时地球半径取 6371 还是 6378.1 km，差 0.11%——足够让复现值与论文对不上第四位小数。**距离/时间矩阵必须用官方或指定函数，不许自己写变体**（见 `references/算例与基准.md`）。

**单位混用的机械判定法**（不用猜，能跑出来）：

1. 先看「无法按数值解析」的值有几个。`240cm`、`3 支` 这类值**既不进分位数、也不进规则检查**，
   如果只报缺失率，它们会静默消失——这是比算错更危险的情形。
2. 取这些值的数字部分，乘 10 / 100 / 1000，看是否**恰好命中本列已有的某个值**。
   命中 3 个以上，基本就是同一列里混了两种单位（本例 240/180/150/120/90 全部 ×10 命中 2400/1800/…）。
3. 反过来看整列：离散型数值列里有 ≥3 组值呈 10 倍关系，也提示混单位。
   但**连续量测列（距离、金额）不要用这条**——1.2 与 12 的巧合太多，查了全是噪音。
4. 换算后必须回验：5 张订单换算完是否与图号规格一致；不一致就是猜错方向。

> 判定出来只是「极可能」，不是「已确认」。换算与否要进 D5 决策并留痕，
> 且必须给出**不换算时的后果**（本例：5 张订单被切短 10 倍，实物报废，而目标值只差 0 根——看不出来）。

### 3.5 逻辑冲突与模型不可行

| 症状 | 本质 | 处置 |
|---|---|---|
| 时间窗倒挂（最早 > 最晚） | 数据错 或 业务规则本身矛盾 | 报给用户，二选一：修数据 / 改规则 |
| 需求 > 车辆容量 | 需求本身不可单趟完成 | 拆分配送或多趟，是**建模决策**不是清洗 |
| 容量超载的历史记录 | 现实违规 或 单位错 | 先查单位，再查是否允许超载 |
| 负值（需求、距离、时长） | 退货/冲销 或 录入错误 | 退货类要单独建模，不能当负需求塞进需求参数 |
| 自环、孤立点 | 数据错 或 真实不可达 | 孤立点必须显式处理，否则模型报不可行却找不到原因 |

**这是本篇最重要的一条**：这类冲突**不属于清洗范畴**。正确处理是让它在 Stage 1 的独立校验器里**炸出来**，而不是在预处理阶段偷偷放宽约束、改小需求、合并时间窗。后者会让模型「看起来可行」，但交付的方案在现实中执行不了。

## 4. 清洗的三条铁律

### 铁律 1 · 三层目录，原始只读

```
data/raw/        原始文件，只读；记录来源、下载日期、sha256
data/staging/    清洗后中间层；每个脚本一个产物，可重跑
data/analysis/   进模型的那一份；附生成脚本与参数
```

判据：删掉 `staging/` 和 `analysis/`，能靠脚本一键重建。做不到就说明有手工操作没留痕。

### 铁律 2 · 动作表（每一步都留痕）

| # | 对象 | 动作 | 规则 / 判据 | 影响行数 | 理由 | 可逆 |
|---|---|---|---|---|---|---|
| 1 | orders.distance | 单位换算 | m → km，÷1000 | 12,480 | 与运单系统口径统一 | 是 |
| 2 | orders | 删除 | `weight_kg <= 0` 且无退货标记 | 37 | 录入错误 | 是（raw 保留） |
| 3 | customers | 合并 | 别名表 12 条 | 12 | 主数据未合并 | 是 |
| 4 | demand | 标注保留 | IQR 外点 214 条不删 | 0 | 大促真实高峰 | — |

「影响行数」这一列不是形式主义：**它是你唯一能回答「清洗到底改变了多少」的证据**。

### 铁律 3 · 清洗即参数（把清洗策略当实验因子）

这是 OR 与 ML 最大的操作差异。ML 里换一种填充方式，看精度有没有掉；OR 里换一种清洗策略，**最优解的结构可能变**。所以：

- 至少做三档：**保守**（只删可证错误）/ **基线**（用户认可的口径）/ **激进**（截尾 + 插值 + 聚合）；
- 每档都完整跑一遍求解，比较：目标值、解的结构（路径条数、车辆数、排产顺序）、关键结论；
- 若三档结论**排序一致**，结论可以写「对清洗口径稳健」；
- 若**翻转**，结论降级为「依赖清洗口径」，并把翻转点写进交付物（见 `references/交付规范.md` 的结论分级）。

> 一个只跑过一种清洗策略的「节省 12%」，经不起一句「你把异常值删了会怎样」。

### 反模式（见到就停）

1. 为了让模型可行而删客户 / 放宽时间窗 / 改小需求；
2. 为了让指标好看而排除「难算例」（这是作弊，不是清洗）；
3. 用测试集的结果回头调清洗规则（数据窥探）；
4. 手工在 Excel 里改数，脚本里没有对应步骤；
5. 只保留清洗后的数据，原始文件被覆盖。

## 5. 挖掘：在 OR 里只做三件事

数据挖掘在运筹里不是「跑个聚类看看」，它必须落到模型的具体位置。**落不到位置的挖掘，一律不做**。

| 目的 | 产出 | 进模型哪里 | 常用方法 | 验证方式 |
|---|---|---|---|---|
| **造参数** | 点估计（需求、时长、成本率） | 参数台账 | 回归、时间序列、分组统计 | 留出期误差；误差进灵敏度 |
| **造不确定性** | 分布 / 情景 / 区间 | 随机或鲁棒模型的输入 | bootstrap、分位数回归、情景缩减 | 样本外覆盖率、情景稳定性 |
| **造结构** | 规律 → 约束或初始解规则 | 约束、候选解生成、邻域设计 | 关联规则、序列模式、聚类 | 加与不加的对照实验 |

### 5.1 需求与参数估计

- 必须留出验证期（不能全样本拟合再全样本评估）；
- 报**误差分布**而不只是均值：MAPE 好看不代表高峰时段准；
- 误差如何进模型：把预测区间作为参数区间做灵敏度，或在随机模型里直接用预测分布；
- **不许**把预测值当成确定值写死，然后在结论里说「需求是 100」——那是假设，不是事实。

### 5.2 不确定性与情景

| 要点 | 做法 |
|---|---|
| 情景从哪来 | 历史重抽样（bootstrap）优先；无历史才用参数化生成 |
| 情景数 | 先做 SAA 稳定性：情景数翻倍后目标值变化 < 阈值才算够 |
| 情景缩减 | k-medoids / 快速前向选择；缩减前后要比较解的质量 |
| 验证 | 样本外覆盖率：名义 95% 服务水平，实测覆盖是否接近 |

### 5.3 聚类与聚合（降规模）

把 5000 个客户聚成 200 个簇再规划，是常见做法，但**必须报两个数**：

1. **聚合误差**：簇内最大半径、簇需求之和与原值偏差、簇内时间窗交集是否为空；
2. **解质量损失**：聚合解回代到细粒度算例后的真实目标值，与直接在细粒度上求解（或下界）比 gap。

> 只报「聚类轮廓系数 0.7」是没有意义的——轮廓系数不告诉你路径方案损失了几个百分点。

### 5.4 关联与驱动因素

用途只有一个：**挑灵敏度参数**。找出「哪些因素与成本/时长强相关」，然后在 Stage 5 优先对这些参数做扰动。

禁令：不写因果。「A 与 B 相关」不能写成「A 导致 B」，除非有实验设计或工具变量。

### 5.5 异常检测：一个算法，两种相反用途

| 用途 | 目标 | 处置 |
|---|---|---|
| 找**脏数据** | 排除错误记录 | 修正或删除，留痕 |
| 找**真实极端事件** | 识别压力场景 | 保留，单独作为鲁棒性算例 |

同一个 Isolation Forest 跑出来的结果，落在哪个用途上，取决于**业务可解释性核查**，不取决于分数。分数高但业务能解释 → 真实事件；分数高且无法解释 → 脏数据候选。

### 5.6 距离 / 时间矩阵：这是口径核算，不是挖掘

- 用官方/指定函数，不自己写变体；
- 记录：坐标系、地球半径、是否含路网、速度假设、是否含装卸；
- 抽样 20 对点做**双向一致性**检查（A→B 与 B→A 是否一致，非对称路网除外）；
- 与真实导航抽样比对，报平均偏差——这是「距离参数可信吗」的唯一证据。

### 5.7 加工时间是否随机台变：$p_j$ 还是 $p_{ij}$

这是**最容易漏、后果最大**的一条口径。数据里通常每张单只在**一台机器上干过一次**，
记下那次的实际工时。于是有两个读法：

| 读法 | 含义 | 模型 | 后果 |
|---|---|---|---|
| $p_j$ 常数 | 工时是「活的性质」，换台机也一样 | $Q\parallel C_{max}$（只差速度） | 「挪到快机」没有额外收益，只做负荷均衡 |
| $p_{ij}$ 机台相关 | 工时是「活在这台机上的耗时」 | $R\parallel C_{max}$（无关机） | 挪到快机真的省时间，优化空间更大 |

**判定法（三步，全部可跑）**：

1. 分层看比值：按机台分组，算 `工时 ÷ 工作量代理`（张数、件数、面积、吨位）的中位数，三台机差多少。
   差 < 15% → 常数足够；差 > 30% → 必须建 $p_{ij}$。
2. 回归定量：$\log(\text{工时}) = a + b\log(1+\text{工作量}) + \text{产品哑变量} + \text{机台哑变量}$，
   $\gamma_m=\exp(\text{机台系数})$。实测：387 行、$R^2=0.93$、$\gamma=$ 1 / 1.371 / 2.580，
   与设备额定速度（1 / 0.72 / 0.38 → 1 / 1.39 / 2.63）几乎重合。
3. 口径对照：两种读法各求一遍最优解，比较目标值。若单周差 > 5%，**必须**把两种口径都报，
   并在交付里说明「按周下派工单时用哪一种」。

**两个陷阱**：

- $\gamma$ 会把「设备专门接难单」这种**选择偏差**吃进去。它只能用于「同一批活换台机」的相对换算，
  不能当设备额定能力、更不能对外报价。要校准就用设备参数或做一次换机实测。
- 机台相关的工时**必须与该机的日强度同单位**：$L_m$ 用 m-机时，$c_m$ 用 m-机时/作业日，
  比值才是「天」。混着算是这类模型最常见的量纲错。

## 8. 禁令（与 SKILL.md 红线对应）

1. 未经 D3 授权，不改原始文件、不删记录；
2. 不因「模型更好解」而删数据——这是最隐蔽的作弊；

6. 不用测试集结果回头调清洗或调挖掘模型；
7. 不把相关性写成因果；
8. 不把预测值当既定事实写进模型参数表而不标 `[假设]`；
9. 不报「聚类质量」代替「解质量损失」；
