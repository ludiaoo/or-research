# 求解器调优手册

> 用途：当使用者**只想用求解器把模型解出来**（M1 = 求解器直用）时，本 skill 的主战场从「设计算法」切到「让求解更快、更稳、更可复现」。
> 这时不写元启发式、不做算法对比，**全部产出围绕「同一模型、更少时间、同样的解」**。
>
> 一句话纪律：**加速不许改解**。文档里每一个「快了 N 倍」，都必须同机、同线程、同时限、同目标值。

---

## 0. 先确认是不是这条路

| 你的处境 | 该走哪条 | 主要产出 |
|---|---|---|
| 模型已定，只想快点解出来 / 解更大规模 | **求解器直用**（本文） | 调优前后对照表 + 可复用参数档 + 规模边界 |
| 模型能解，但想要更好的解、规模远超求解器能力 | 自研算法（`算法手册.md`） | 算法 + gap 表 |
| 想要下界、最优性证书、论文级证据 | 完整研究（8 检查点） | 下界 + 证书 + 统计 |

判断信号：**你要的是「一个能用的解」，还是「一个能证明的说法」？** 前者调优，后者要下界。

进这条路之前必须先回答三个问题（对应决策点 M1–M3）：

1. 优化的是哪个时间？**总求解时间 / 首个可行解时间 / 证明最优时间**——三者调法不同，甚至相反。
2. 允许动到哪一层？**只调参数 / 动本次研究的 formulation / 动求解方式（分解、warm start）**——对象是本轮自己写的模型，不涉及他人代码或原文。
3. 目标规模是多少？调优只在**目标规模**上有意义，在小算例上调出来的参数到大算例经常反向。

## 1. 优化顺序：四层，从便宜到贵

按投入产出排序。**L1 没做完就调参数，是最常见的浪费**——用错 formulation 时，参数只能救回 10%，重写约束能救回 90%。

### L1 建模层（改模型，不改参数）—— 收益最大，风险最低

| 手段 | 什么时候用 | 怎么判断有效 |
|---|---|---|
| **收紧 Big-M** | 有任何 `M(1-y)` 项 | 用变量自身 $ub$ 推出最小合法 M；M 从 1e4 降到 1e2 常直接砍掉一半节点 |
| **变量上界传播** | 时间/流量变量边界是「拍的大数」 | 用路径长度和推 $ub$；界紧一档，LP 界立刻抬 |
| **消除对称** | 同构实体（同型车、同型机、同班组） | 加序关系 $i<j$ 或按索引破对称；节点数常降一个量级 |
| **聚合冗余约束** | 有「逐条」与「聚合」两版 | 用 `milp_lab compare` 实测：**约束多 ≠ 更快**（mFSTSP 实测 disagg 1927 条约束反而 1 节点解完，agg 1585 条要走 449 节点） |
| **指示约束代替 Big-M** | 支持 indicator 的求解器 | 通常 LP 界更紧；但会削弱 presolve，需实测 |
| **量纲缩放** | 系数跨 1e-3 ~ 1e6 | 时间以秒、成本以千元为单位；数值警告消失、节点变少 |
| **稀疏化** | 约束里有大量零系数项 | `nnz` 降一半，每节点 LP 快一倍 |
| **给初始可行解** | 有构造解/历史方案 | 作为 MIP start，省掉找首个解的时间（见 L3） |

> 判据：L1 每改一项都要留「改前 / 改后」的 LP 界与节点数。**只报总时间变化是无法归因的**。

### L2 参数层（不改模型）—— 收益中等，成本极低

先诊断「卡在哪」，再选参数，不要盲扫：

| 症状 | 病因 | 先试这些参数 |
|---|---|---|
| 根节点 gap 就很大，树很小 | LP 松弛弱 | `Cuts=3`、`GomoryPasses`↑、（更好的是回 L1 换 formulation） |
| 节点数爆炸、每节点很快 | 对称 / 分支决策差 | `Symmetry=2`、`VarBranch`、`MIPFocus=3` |
| 每节点很慢、树不大 | LP 大或数值病态 | `Method`、`NumericFocus=3`、`MarkowitzTol`、回 L1 缩放 |
| 长时间拿不到可行解 | 启发式不够 | `Heuristics=0.5`、`MIPFocus=1`、给 MIP start |
| 解已很好但证不出最优 | 界推进慢 | `MIPFocus=3`、`Cuts=2~3` |
| 解校验出现微小违约 | 数值容差 | `NumericFocus=3`、`FeasibilityTol`、`IntFeasTol` 谨慎调整并记录 |
| presolve 吃掉大量时间 | 模型超大规模 | `Presolve=1`、`AggFill=0` |
| 内存爆 | 树太大 | `NodefileStart`、减少 cuts、先 L1 降规模 |

参数档实测对比：`scripts/solver_bench.py`（同一模型、同线程、同时限，跑完自动比对目标值）。

### L3 求解方式层（改求解流程）—— 收益大，成本也大

| 手段 | 适合 | 代价 / 坑 |
|---|---|---|
| **MIP start / warm start** | 有历史方案或构造解 | 只影响找解，不影响证明；解不可行会让求解器直接忽略（要看日志确认接受） |
| **UB 作 cutoff** | 已有较好可行解 | 设 `Cutoff` 可剪枝，但设错（低于真最优）会直接判无解 |
| **fix-and-optimize / 滚动时域** | 超大规模、结构可分块 | 得到的是启发式解，**没有最优性证书**，必须改口径 |
| **Benders / Lagrangian 分解** | 有明显主从结构 | 实现成本高；收敛慢时要调稳定化 |
| **列生成 / 分支定价** | 变量极多、约束少 | 见 `算法手册.md` §2.4；工程量大 |
| **加有效不等式** | 有已知的强不等式族 | 加错会切掉最优解——必须在小算例上验证不切 |

> L3 一旦做了，结论口径就变了：**从「最优」降级为「启发式解 + 相对 UB 的 gap」**。这一点必须写进交付物，不许含糊。

### L4 口径层（只改怎么量，不改解）—— 最容易变成造假

- `MIPGap=1e-4` 就宣称「最优」= 错。要么 `MIPGap=0`，要么写「gap ≤ 0.01%」。
- 时限截断的时间只能读作「到此为止」，不能与其他档案比快慢。
- `Threads>1` 会同时破坏时间可比性与结果可复现性；对外报数固定 `Threads=1`。
- 只报「最快那一次」= 选择性报告。至少 2 次，报中位数与极差。

## 2. 诊断表：先定位，再调参

按求解日志的顺序排查，**不要跳步**：

| 现象 | 第一嫌疑 | 验证方法 | 处置 |
|---|---|---|---|
| LP 界 = 0 或远离常识 | formulation 退化（如 makespan + Big-M 全 $t=0$ 可行） | 令全连续变量取下界，看是否可行 | 换目标做分离实验，或加有效不等式；**别在参数上浪费时间** |
| 根节点 gap 大 | 松弛弱 | 看 log 的 `Root relaxation` 与 `Best bound` | L1 收紧 M / 换 formulation → 再 `Cuts=3` |
| 节点数 10 万+ 但每节点 < 0.01s | 对称或分支差 | 看 `Explored` 与 `Depth` | `Symmetry=2`、`MIPFocus=3` |
| 每节点 > 0.1s | LP 太大/病态 | 看 `Iters/Node`、是否有数值警告 | L1 缩放与稀疏化、`NumericFocus=3` |
| 30% 时间在 presolve | 模型冗余 | `Presolve=0` 对照一次 | `AggFill=0`、去冗余行 |
| 反复 `numerical trouble` | 系数跨度大 / 大 M | 查系数范围 | 缩放、收紧 M、`NumericFocus=3` |
| 内存持续涨 | 树太大 | `NodefileStart` | 落盘节点、减 cuts |

## 3. 参数速查（Gurobi ↔ HiGHS）

| 目的 | Gurobi | HiGHS（scipy `milp` 暴露的部分） |
|---|---|---|
| 时限 | `TimeLimit` | `options={"time_limit": s}` |
| 相对 gap | `MIPGap` | `options={"mip_rel_gap": g}` |
| 预处理 | `Presolve` 0/1/2 | `options={"presolve": True/False}` |
| 节点上限 | `NodeLimit` | `options={"node_limit": n}` |
| 割平面强度 | `Cuts` 0–3 | 不暴露 |
| 可行解优先 | `MIPFocus=1`、`Heuristics` | 不暴露 |
| 最优证明优先 | `MIPFocus=3` | 不暴露 |
| 对称破除 | `Symmetry` 0–2 | 不暴露 |
| 数值稳健 | `NumericFocus` | 不暴露 |
| 线程 | `Threads` | 单线程 |
| 初始解 | `Start` / `MIPStart` | `options={"mip_start": ...}`（版本相关） |

> 没有 Gurobi 时，参数层能做的只有预处理与时限；**这时收益主要在 L1**，别在文档里假装做过参数对比。

## 4. 三条硬约束

1. **加速不许改解**：同一模型、同一 gap 目标下，各档案的 `ObjVal` 必须一致（相对差 ≤ 1e-6）。不一致就是换了答案。
2. **同口径才可比**：同机、同线程、同 seed、同时限、同 gap。换算例、换机器、换线程数的时间差不是加速。
3. **只报分布，不报幸运值**：≥2 次重复，报中位数与极差；至少固定 seed。

`solver_bench.py` 会把这三条做成硬检查：目标值不一致直接打 ❌，出现 `LIMIT` 提醒该行不可比。

## 5. 度量协议

一次合格的「加速」报告必须有以下四组数：

| 指标 | 为什么 | 怎么取 |
|---|---|---|
| 求解总时间 | 主指标 | 中位数，≥2 次 |
| 节点数 | 区分「树小了」还是「每节点快了」 | 日志 `NodeCount` |
| 根节点 LP 界 / 根 gap | 判断是不是 L1 起的作用 | 日志 `Root relaxation` |
| 首个可行解时间 | 业务只关心「多久能给方案」时这才是主指标 | 用 `SolutionLimit=1` 单独跑一臂，或看日志首个 incumbent |

**加速比的分母必须自己重跑**：不能拿"上次用默认参数跑了 60 秒"当 baseline，机器状态、求解器版本都会变。

判定规则：

- 更快 + 同解 + 同 status → 真加速。
- 更快 + gap 更大 → **没加速，只是提前停了**。
- 更快 + 解不同 → 参数改变了搜索路径，先查是不是时限截断。
- 更慢但界更紧 → 对「证明最优」是好事，对「尽快给方案」是坏事，按 M2 的口径判。

## 6. 实测样例（mFSTSP 8 客户，接力链 MILP）

模型：478 变量（415 二元）/ 1588 约束 / nnz 11934，目标 makespan，最优 1048.716531。
口径：`Threads=1`、`Seed=0`、`TimeLimit=120`、`MIPGap=0`，每档 1 次。

<!-- BENCH_TABLE -->

| 档案 | 关键参数 | 目标值 | 节点 | 时间 (s) | 相对 baseline | 状态 |
|---|---|---|---|---|---|---|
| baseline | 默认 | 1048.716531 | 37 858 | **11.86** | 1.00× | OPTIMAL |
| presolve | `Presolve=2, AggFill=0, PreDual=0` | 1048.716531 | 38 704 | 13.94 | 0.85× | OPTIMAL |
| cuts | `Cuts=3, GomoryPasses=2` | 1048.716531 | 32 566 | 41.49 | 0.29× | OPTIMAL |
| mipfocus_feas | `MIPFocus=1, Heuristics=0.5` | 1048.716531 | 106 931 | 56.10 | 0.21× | OPTIMAL |
| mipfocus_bound | `MIPFocus=3, Cuts=2, Symmetry=2` | 1058.525714 | 86 807 | 60.03 | 不可比 | **LIMIT**（gap 73%） |
| symmetry | `Symmetry=2, Presolve=2` | 1048.716531 | 38 704 | 14.86 | 0.80× | OPTIMAL |
| numeric | `NumericFocus=3, MarkowitzTol=0.01` | 1048.716531 | 30 295 | 16.11 | 0.74× | OPTIMAL |

**结论一：这次没有一个参数档比默认更快，最好的档就是默认。** 参数层不是万灵药。
七档里六档证到同一个最优值（解一致，说明参数没改可行域），但时间全部 ≥ baseline；`mipfocus_bound` 甚至 60 s 没证完、incumbent 还差 0.94%——它失败得最彻底，恰恰因为它把力气花在"改界"上，而本模型的界本来就极弱。

**结论二：节点数下降 ≠ 时间下降。** `cuts` 把节点从 37 858 降到 32 566（−14%），时间却涨到 3.5 倍——每节点慢了 3.6 倍。只报节点数会得出完全相反的结论。

**结论三：真正有效的加速不在参数里。** 同一模型、同一台机器：

| 口径 | 时间 | 结果 |
|---|---|---|
| `Threads=1` | 120 s（截断） | 未证最优，best bound 168.09 vs obj 1048.72，gap 84% |
| `Threads=0`（自动，本机多核） | **11.24 / 11.48 / 11.86 s** | OPTIMAL |

**>10 倍**。但这是"用满机器"，不是"算法更快"——报告里必须分开写，否则等于把硬件当方法。

**结论四：调不动的时候要回 L1。** 本模型的 LP 界恒为 0（令全 $t=0$ 即可行，makespan + Big-M 的经典退化），根节点就没什么可割的，参数层自然使不上劲。这种模型想快，只能换 formulation、加有效不等式或改用接力链这类结构约束——`cuts` 的实测反而变慢，正是"给退化模型加割"的典型结果。

> 方法论提醒：**这四条结论都只对"这一个模型、这台机器"成立**（红线 25）。它们的价值不在于"参数 A 比 B 好"，而在于示范一份调优报告该怎么写：给口径、给一致性检查、给失效项、给归因，而不是只给一个加速比。

结论要按「哪一层起作用」读，不要按「哪个参数名字好听」读。

## 7. 常见反模式

1. **先调参，后建模**：formulation 弱的时候调参是在给漏水的桶打补丁。
2. **盲扫参数网格**：7 个参数各 3 档 = 2187 次运行，绝大多数结论不可外推。**按症状选参数**。
3. **`Threads=0` 报时间**：跑分好看，不可复现，不能进交付物。
4. **拿 `MIPGap=1e-4` 的解当最优**：差 0.01% 在百万级目标上就是几千块。
5. **把 warm start 的效果算进"算法更快"**：warm start 来自别的方法，功劳要分开记。
6. **只在小算例上调参再套大算例**：参数最优值随规模漂移，必须给出「大算例重调」的说明。
7. **加速后不重跑校验器**：参数改了、数值容差变了，解可能从可行变到差 1e-5 违约。
8. **把「解出来」当「解决了」**：调优只回答「多快」，不回答「这个模型对不对」——正确性仍要靠独立校验器与 `milp_lab check`。

## 8. 交付物

走这条路时，交付物是这四样（不是一篇论文）：

1. **调优前后对照表**：时间 / 节点 / 根 gap / 首个可行解时间，附口径。
2. **参数档文件**：可直接复用的参数集合 + 每个参数"为什么是这个值"。
3. **规模边界**：这套配置在多大规模内能解到最优、超界后给什么（解 + gap）。
4. **复现命令**：一行能重跑出同一张表的命令。

对应检查点：`04_精确解与下界.md` §7 求解性能档案；阶段门判据 Stage 4 的加速对比条目。
